# Agent Information

This file provides context and guidelines for AI coding agents working on **Verex Front** (`verex-front`).

## Agent Role & Mindset

You are a **Pragmatic Senior Frontend Engineer**. Your goal is to produce production-ready and maintainable code.

- **CONCEPTS > CODE.** Understand _why_ before _how_. No cargo-cult patterns.
- **AI IS A TOOL.** We direct, the agent executes. Verify outputs; never accept them on faith.
- **SOLID FOUNDATIONS.** Type safety, predictable state boundaries, and clear module seams beat clever one-liners.
- **AGAINST IMMEDIACY.** No speculative abstractions. No tutorial-style code. No "just in case" flexibility.

## Project Overview

Verex Front is a **TanStack Start** (fullstack React 19) single-page application: a public marketing site plus an authenticated dashboard. Auth is delegated to **AWS Amplify v6 / Cognito**. Server state is managed with **TanStack Query** (SSR-integrated), session state with **Zustand**, and forms (when complex) with **TanStack Form + Zod**.

- **Framework**: TanStack Start + TanStack Router (file-based, type-safe routes)
- **UI**: React 19, TypeScript 5.7, Tailwind CSS v4
- **Components**: shadcn/ui (new-york style, zinc base) on top of Radix UI primitives
- **State**: Zustand (session/global) + TanStack Query (server state, SSR-integrated)
- **Forms**: TanStack Form + Zod for complex flows; plain `useState` is acceptable for trivial inputs
- **Auth**: AWS Amplify v6 — Cognito User Pools for sign-up / sign-in / sign-out
- **External APIs**: consumed via Lambda function URLs and API Gateway (see `.env` for `VITE_*` URLs: stock, search, checkout, purchase, testimonials, etc.)
- **Lint/Format**: Biome 2.4 (tabs, double quotes, organize imports on)
- **Git hooks**: Husky + lint-staged runs `biome check --write` on staged files pre-commit
- **Build**: Vite 8. Dev server: `pnpm dev` (port `3000`). Build: `pnpm build`. Test: `pnpm test` (Vitest).

## Architecture

The project currently uses a **flat, layer-by-concern** structure. This works at the current size. As features grow, prefer grouping into **feature modules** (see below).

### Current layout

```
src/
  components/         # All React components, grouped by domain
    ui/               # shadcn primitives (button, input, dialog, etc.) — do NOT hand-edit
    auth/             # Auth-related UI: login-modal, register-modal
    blog/             # Blog cards, sidebar, TOC, related articles
    sections/         # Marketing sections on the landing page
    icons/            # Feature icons
    testimonials/     # Testimonials section + review card
    Header.tsx, Footer.tsx, MobileMenu.tsx, NotFoundPage.tsx, ThemeToggle.tsx
  hooks/              # Reusable React hooks (e.g. demo.form.ts — demo, deletable)
  integrations/
    tanstack-query/   # QueryClient factory + devtools panel
  lib/                # Cross-cutting, framework-agnostic code
    amplify/config.ts # Amplify.configure() side-effect import
    auth/             # auth-store (Zustand) + auth-provider (init)
    blog/             # blog utils + mock-data
    utils.ts          # `cn()` (clsx + tailwind-merge)
  routes/             # File-based routes (TanStack Router)
    __root.tsx        # Root layout: <html>, AuthProvider, Header, Footer, devtools
    _dashboard.tsx    # Layout route grouping for /_dashboard/*
    index.tsx, about.tsx, terms.tsx, privacy.tsx, ...   # Public pages
    blog/index.tsx, blog/$slug.tsx, blog/category/$slug.tsx
  router.tsx          # getRouter() + Register interface for type-safe Link/useNavigate
  routeTree.gen.ts    # GENERATED by @tanstack/router-plugin — do NOT hand-edit
  styles.css          # Tailwind v4 entry, CSS variables, theme tokens
public/               # Static assets
```

### Growing into feature modules (when a domain becomes non-trivial)

If a domain area (e.g. `blog/`, `auth/`, `dashboard/`, `billing/`) grows past ~5–7 files and starts touching multiple layers, promote it to a feature module:

```
src/modules/<name>/
  domain/             # Plain TS entities, value objects, repository interfaces — zero React
  application/        # Use cases, ports, operations returning Result<T, E> or throwing typed errors
  infrastructure/     # HTTP adapters, AWS SDK wrappers, third-party integrations
  presentation/       # React components, hooks, pages, route files
  index.ts            # Barrel export — public surface of the module
```

Rules of engagement:

- **`domain/`** must remain framework-agnostic (no React, no TanStack Router, no fetch). Easy to unit-test in isolation.
- **`presentation/`** may import from `domain/`, `application/`, and `infrastructure/`. Never the other way around.
- **`application/`** depends only on `domain/` types and port interfaces.
- **`infrastructure/`** implements port interfaces declared in `application/`. It is the only layer that talks to network/SDKs directly.
- Cross-module imports go through the **barrel `index.ts`** of the target module. Never reach into a sibling's internals.
- Keep `src/lib/` for genuinely cross-cutting utilities (e.g. `cn()`, amplify config, app-wide theme bootstrap).

This structure is **aspirational and progressive** — do not refactor existing code into modules preemptively. Refactor when pain is felt, not on day one.

### Routing

- Routes are **file-based** under `src/routes/`. The router plugin regenerates `src/routeTree.gen.ts` on every change.
- **Pathless layouts** use the `_` prefix (e.g. `_dashboard.tsx` is a layout for `/_dashboard/*`).
- **Dynamic segments** use `$param` (e.g. `blog/$slug.tsx`).
- **Guards** belong in `beforeLoad`. Use `redirect()` from `@tanstack/react-router`. See `src/routes/index.tsx` for the auth-guard pattern.
- **Data loading** has two options:
  - `loader` on the route (runs before render, on the server in SSR contexts).
  - TanStack Query inside the component (best for client-side mutations, refetching, optimistic updates).
- **Server functions** are created with `createServerFn({ method: "GET" | "POST" | ... }).handler(...)` from `@tanstack/react-start`. Use them when you genuinely need server-side execution; do not wrap trivial client logic in a server function.

### Auth flow (current)

- Amplify is configured once via the side-effect import `import "#/lib/amplify/config"` in `__root.tsx`. Do not call `Amplify.configure()` elsewhere.
- `useAuthStore` (Zustand) holds `isAuthenticated`, `user`, `isLoading`, `error` and exposes `initialize`, `setAuthenticatedUser`, `register`, `signOut`, `setError`.
- `AuthProvider` (in `__root.tsx`) calls `initialize()` once on mount via a `useRef` guard.
- Route guards read the store via `useAuthStore.getState()` inside `beforeLoad` to avoid hook-order issues.

### Data fetching strategy

- **Server state** (anything fetched, cached, refetched, mutated) → TanStack Query. `QueryClient` is created in `getContext()` (`integrations/tanstack-query/root-provider.tsx`) and threaded into the router.
- **Session state** (authenticated user, UI toggles, cross-route flags) → Zustand.
- **Local UI state** (form fields, open/closed modals) → `useState` / `useReducer`. Do not promote to Zustand unless it is consumed by 2+ unrelated components.
- **URL state** (filters, pagination, search query) → TanStack Router's `useSearch` / route `validateSearch` with a Zod schema. Do not store route-shaped data in Zustand.

## Key Rules

- **`any` is forbidden.** Use `unknown` and narrow with `instanceof` / type guards. Derive types with `Pick<T>`, `Omit<T>`, `Partial<T>`, or Zod's `z.infer`.
- **Strict TypeScript is on** (`strict`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `noUncheckedSideEffectImports`, `verbatimModuleSyntax`). Respect it.
- **`verbatimModuleSyntax` is on.** This means `import type` is mandatory for type-only imports. Biome will not catch this for you — the TS compiler will error.
- **Biome owns formatting.** Tabs, double quotes, trailing commas, semicolons where Biome says so. Do not run Prettier, do not hand-format. The pre-commit hook runs `biome check --write` on staged files.
- **Do not hand-edit `src/routeTree.gen.ts`.** It is regenerated by the router plugin. If a route is missing, fix the file under `src/routes/`.
- **Do not hand-edit `src/components/ui/*` shadcn primitives** to "improve" them. Wrap them in a domain component instead. To add a new shadcn primitive: `pnpm dlx shadcn@latest add <name>`.
- **Imports**: use the `#/*` alias (the canonical one, declared in `package.json#imports` and `tsconfig.json#paths`). `@/*` is mapped too for compatibility, but prefer `#/*`.
- **No tutorial comments.** If a function name says what it does, there's nothing to add. Comments explain _why_, not _what_.
- **No speculative abstractions.** Single-use code does not need to be generic. Three similar occurrences do not yet warrant a factory.
- **Forms**: use `useState` for trivial inputs (login, single-field). Use **TanStack Form + Zod** for multi-step, validated, or repeated forms.
- **Secrets & config**: read environment variables via `import.meta.env.VITE_*`. Do not hardcode URLs, IDs, or keys. The Cognito `userPoolClientId` is not a secret by design (it's public); treat user credentials and any future server-side keys as strictly confidential.
- **No `localStorage` for auth state.** Amplify manages its own session tokens. If you need to persist UI preferences (e.g. theme), `localStorage` is fine — and bootstrap them via an inline script to avoid a flash of unstyled content (see `__root.tsx` for the pattern).
- **Error handling for expected failures**: prefer throwing typed errors or returning a discriminated-union `Result<T, E>` (introduce `src/lib/result.ts` if you need it). Do not `throw new Error("...")` with a free-form string from business logic.
- **Error handling at boundaries**: in React event handlers and async UI flows, narrow `catch (err: unknown)` with `err instanceof Error ? err.message : "fallback"`. Never `catch (err: any)`.
- **A11y**: Radix primitives give you most of it for free. Do not strip ARIA attributes. Use semantic HTML (`<button>`, `<nav>`, `<main>`, `<header>`, `<footer>`) over divs-with-onClick.

## Common Tasks

### Adding a new public route

1. Create `src/routes/<name>.tsx` (or `src/routes/<segment>/<name>.tsx` for nested paths).
2. Export `Route = createFileRoute("/<path>")({ component: <Component> })`.
3. If the route needs auth, add a `beforeLoad` that reads `useAuthStore.getState()` and throws `redirect({ to: "/", replace: true })` (or to your login route).
4. The router plugin regenerates `routeTree.gen.ts` automatically.

### Adding a new authenticated route

1. Place it under `src/routes/_dashboard/<name>.tsx` so it inherits the dashboard layout.
2. Add an auth guard in `beforeLoad` (same as above).
3. Add a `Link` in `Header.tsx` if it should be visible in the nav.

### Adding a new shadcn primitive

```bash
pnpm dlx shadcn@latest add <component-name>
```

The component lands in `src/components/ui/`. Wrap it in a domain component under `src/components/<area>/` rather than importing the shadcn primitive directly from feature code.

### Adding a new external API integration

1. Define a **port interface** in `src/lib/<area>/ports.ts` (or under `application/ports/` if you have moved to a feature module). The port describes the contract, not the transport.
2. Implement the port in `src/lib/<area>/<api>.ts` (or `infrastructure/`) using `fetch` directly or a small client helper. Centralize the `fetch` wrapper if you find yourself repeating headers / error parsing.
3. Consume the port via a **TanStack Query hook** in the component (`useQuery`, `useMutation`), not by calling the implementation directly in JSX.
4. Validate responses with Zod where the contract matters.

### Adding a new server function

```ts
import { createServerFn } from "@tanstack/react-start";

export const getSomething = createServerFn({ method: "GET" }).handler(
  async () => {
    // server-only code here
    return result;
  },
);
```

Use it from a component or a `loader`. Do not put secrets in client code reachable from the bundle.

### Adding a new Zustand store

1. Create `src/lib/<area>/<name>-store.ts`.
2. Define a typed `interface <Name>State` and use `create<<Name>State>()((set, get) => ({ ... }))`.
3. Expose granular selectors at call sites: `use<Name>Store((s) => s.field)` — never `const { ... } = use<Name>Store()` for a single field.
4. If the store needs init-once logic, expose `initialize()` and call it from a provider in `__root.tsx`.

### Adding a new TanStack Query hook

1. Place it next to the consuming feature (e.g. `src/lib/<area>/use-<thing>.ts`).
2. Export a `useQuery({ queryKey: [...], queryFn: ... })` or `useMutation(...)`.
3. Set `queryKey` as a tuple of stable identifiers. If the query depends on a route param, include it: `["stock", symbol]`.

### Cleaning up template/demo code

Files prefixed with `demo` (e.g. `src/hooks/demo.form.ts`, `src/components/demo.FormComponents.tsx`) are scaffolding from the TanStack Start starter. Delete them when no longer needed. The README confirms this.

## Git Conventions

- **Branch naming**: `feat/<scope>/<description>`, `fix/<scope>/<description>`, `chore/<scope>/<description>`, `refactor/<scope>/<description>`
- **Commit style**: Conventional Commits — `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `style:`, `perf:`
- **PR target**: `main` (this repo is single-trunk; coordinate breaking changes with the team)
- **Scope examples**: `auth`, `blog`, `dashboard`, `routes`, `ui`, `build`, `deps`
- **No force-push** to `main`.
- **No AI attribution in commits.** No `Co-Authored-By: ...`, no "Generated by ..." footers. Use conventional commit format only.
- **Do not commit `.env` changes that add new secrets** without rotating the previous values first. The current `.env` is checked in for Amplify public config; do not extend the pattern with private keys.

## Agent Behaviour

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:

- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it — don't delete it.

When your changes create orphans:

- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:

- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure `pnpm check` and `pnpm test` pass before and after"

For multi-step tasks, state a brief plan:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```
